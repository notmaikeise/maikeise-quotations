## 1. Objective

Sprint 01 aimed to implement the first functional backend flow of **Maikeise Quotations**, establishing the quotation domain, its primary business rules and the initial persistence layer using Google Sheets.

The implementation also aimed to keep business rules decoupled from infrastructure, following the architectural decision established in **ADR-001**.

At the end of this sprint, the system should be able to receive quotation data, validate it, calculate derived values, identify possible duplicates and persist both the quotation and its complementary data in the DEV environment.

## 4. Domain Model

The `Quotation` entity represents a quotation within the system.

It contains the required commercial information and domain behavior without directly depending on Google Sheets or `SpreadsheetApp`.

One of its responsibilities is calculating the total value:

```text
TOTAL_VALUE = QUANTITY × UNIT_VALUE
```

The total value is considered system-derived data.

Therefore, users are not responsible for manually providing a total that could become inconsistent with quantity and unit value.

---

## 5. Business Rules

The initial domain rules include:

- quantity must be greater than zero;
- unit value cannot be negative;
- total value must be calculated by the system;
- NCM must contain exactly eight digits;
- requested date must represent a valid date;
- required fields cannot be empty;
- every quotation receives a unique identifier;
- new quotations receive the `ACTIVE` status;
- new records start at version `1`;
- creation and update timestamps are generated by the application.

## 6. Main Fields

The main quotation structure contains:

```text
RFP
Item code
Reference
Description
Supplier
Quantity
Unit value
Total value
NCM
Lead time
Payment
Delivery
Requested date
```

The system also maintains technical metadata:

```text
ID_COTACAO
STATUS
CRIADO_EM
ATUALIZADO_EM
VERSAO
```

RFP, item code and NCM are handled in a way that preserves their textual representation, including leading zeros when applicable.

---

## 7. Validation

Business-rule validation is handled by:

```text
QuotationValidator
```

The validator belongs to the domain layer and does not depend on the user interface or persistence mechanism.

Flow:

```text
Received data
      ↓
Quotation
      ↓
QuotationValidator
      ↓
Valid quotation?
   ↙       ↘
  NO       YES
  ↓         ↓
Error    Continue
```

This prevents fundamental business rules from depending exclusively on browser-side validation.

---

## 8. Possible Duplicate Detection

The system performs an initial check for potentially duplicated records.

The current combination is:

```text
RFP
+
Item Code
+
Supplier
```

A possible duplicate does not prevent registration.

Instead, the application returns a warning that can later be displayed by the presentation layer.

Example:

```text
Possible duplicate found
        ↓
      Warning
        ↓
Registration remains allowed
```

This avoids incorrectly blocking legitimate quotations that share similar information.

---

## 9. Repository Pattern

Data access is abstracted through repository contracts.

Example:

```text
QuotationRepository
        ↓
GoogleSheetsQuotationRepository
        ↓
SpreadsheetApp
        ↓
Google Sheets
```

The domain knows the persistence contract it requires without needing to know which technology implements it.

This reduces direct coupling to Google Sheets.

---

## 10. Portability

This separation allows an implementation such as:

```text
GoogleSheetsQuotationRepository
```

to eventually be replaced by:

```text
PostgreSQLQuotationRepository
```

or another technology while preserving most business rules and application services.

This strategy follows the portability principle established in ADR-001.

## 11. QuotationService

`QuotationService` coordinates the quotation registration use case.

The current flow is:

```text
Input
   ↓
QuotationService
   ↓
Create Quotation
   ↓
Validation
   ↓
Duplicate Check
   ↓
Quotation Persistence
   ↓
Optional Data Persistence
   ↓
Result
```

The presentation layer therefore does not need to understand persistence implementation details.

---

## 12. Persistence

Quotations are initially persisted in:

```text
COTACOES
```

During creation, the system generates or controls:

```text
UUID
STATUS
CRIADO_EM
ATUALIZADO_EM
VERSAO
TOTAL VALUE
```

Quotation writes use `LockService` to reduce problems related to concurrent writes.

Persistence operations use batch writes whenever practical.

---

## 13. Optional Data

Not every piece of information found in a quotation needs to permanently belong to the primary schema.

To provide flexibility, the following structure was implemented:

```text
DADOS_OPCIONAIS
```

Containing:

```text
ID_DADO
ID_COTACAO
CHAVE
VALOR
ORDEM
```

Example:

```text
Quotation
│
├── RFP
├── Supplier
├── Quantity
├── NCM
│
└── Optional Data
    ├── CURRENCY = BRL
    ├── REGION = Southeast
    ├── COST_CENTER = DEMO-1001
    └── OBSERVATION = ...
```

This allows new attributes to be incorporated without continuously modifying the primary `COTACOES` structure.

---

## 14. Batch Persistence

Optional data is persisted using a batch operation.

Instead of:

```text
Field 1 → write
Field 2 → write
Field 3 → write
Field 4 → write
```

the application prepares the records and performs a single write operation:

```text
Fields 1..N
     ↓
setValues()
```

This approach reduces unnecessary Google Sheets operations.

## 17. Known Limitations

The current persistence layer uses Google Sheets, which does not provide ACID transactions equivalent to those available in relational databases.

A scenario such as the following is currently possible:

```text
Quotation
   ↓
COTACOES
   ↓
SAVED ✓

Optional Data
   ↓
DADOS_OPCIONAIS
   ↓
ERROR ✗
```

This may result in partial persistence.

Additional mechanisms for:

- rollback;
- failure recovery;
- atomicity;
- complete auditing;
- advanced concurrency strategies;

have deliberately been postponed to a later stage.

This is a known limitation and must be considered as the architecture evolves.
